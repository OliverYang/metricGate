# MetricGate 竞品调研总结

## 🎯 核心问题

**MetricGate 是一套 CI 能力吗？已有开源工具是否覆盖了类似功能？**

---

## 📊 竞品分类分析

### 1. **传统代码质量门禁工具**

#### SonarQube/SonarCloud
- **定位**: 企业级代码质量管理平台
- **CI 集成**: ✅ 支持 Jenkins/GitLab CI/GitHub Actions
- **核心能力**:
  - 静态代码分析 (多种语言)
  - 安全漏洞检测
  - 代码覆盖率
  - 技术债务管理
  - 质量门禁 (Quality Gates)
- **优势**:
  - 功能全面，生态成熟
  - 可视化仪表盘强大
  - 支持多语言
- **劣势**:
  - 需要服务端部署
  - 反馈慢 (分钟级)
  - Token 成本高 (需上传代码)
  - 配置复杂
  - **不支持架构分层约束**
  - **不支持增量行级检查**
  - **不适合 LLM 场景**

#### CodeClimate
- **定位**: SaaS 代码质量平台
- **CI 集成**: ✅ GitHub/GitLab
- **核心能力**: 代码复杂度、重复率、测试覆盖
- **劣势**: 
  - SaaS 模式，Token 成本高
  - 黑盒，无法自定义规则
  - 不支持架构约束

---

### 2. **Linter 与静态检查工具**

#### ESLint (JavaScript/TypeScript)
- **定位**: 插件化 JavaScript linter
- **CI 集成**: ✅ GitHub Actions
- **核心能力**:
  - 语法检查
  - 代码风格统一
  - 可自定义规则
- **优势**:
  - 轻量级，速度快
  - 插件生态丰富
  - 支持自定义规则
- **劣势**:
  - 仅支持 JS/TS
  - **不支持架构分层**
  - **不支持增量检查**
  - **无团队约束管理**

#### golangci-lint (Go)
- **定位**: Go 代码 linter 聚合器
- **CI 集成**: ✅ GitHub Actions
- **核心能力**:
  - 聚合多个 linter
  - 并行执行
  - 缓存加速
- **优势**:
  - 速度快
  - 配置简单
  - 社区活跃
- **劣势**:
  - **仅静态规则，无架构约束**
  - **全量扫描，无增量**
  - **无业务语义理解**
  - **不适合 LLM 场景**

#### PMD/SpotBugs (Java)
- **定位**: Java 静态分析工具
- **CI 集成**: ✅ Maven/Gradle
- **核心能力**: 代码规范、潜在 bug 检测
- **劣势**: 
  - 仅 Java
  - **无架构约束**
  - **无增量检查**

---

### 3. **架构约束检查工具**

#### ArchUnit (Java)
- **定位**: Java 架构测试库
- **CI 集成**: ✅ JUnit/Maven/Gradle
- **核心能力**:
  - 包依赖方向检查
  - 分层架构验证
  - 循环依赖检测
- **优势**:
  - 深度集成到测试框架
  - 类型系统支持
  - 精确的架构约束
- **劣势**:
  - **仅 Java**
  - **需要类型系统** (编译后才能运行)
  - **无法检查未写完的代码**
  - **不适合 LLM 生成场景**
  - **无实时反馈**

#### ADE (Architectural Decision Enforcement)
- **定位**: 架构决策 DSL 工具
- **核心能力**: 使用 DSL 定义架构规则
- **劣势**:
  - 小众工具
  - 文档不足
  - **无 CI 集成**
  - **无增量检查**

---

### 4. **Policy as Code 工具**

#### Palantir Policy Bot
- **定位**: GitHub PR 审批策略工具
- **CI 集成**: ✅ GitHub App
- **核心能力**:
  - PR 审批流程自动化
  - 基于条件的状态检查
  - 标签管理
- **优势**:
  - 深度集成 GitHub
  - 灵活的审批策略
- **劣势**:
  - **不是代码质量检查**
  - **仅控制审批流程**
  - **不检查代码内容**

#### Kodus
- **定位**: AI 驱动的 Policy as Code 审查
- **核心能力**:
  - Markdown + YAML 定义规则
  - AI 辅助审查
  - PR 范围限制
- **优势**:
  - 规则易写
  - AI 辅助
- **劣势**:
  - **新工具，未经验证**
  - **依赖云端 AI**
  - **Token 成本高**
  - **无架构约束**

#### Semgrep Policies
- **定位**: 安全规则管理平台
- **CI 集成**: ✅ GitHub Actions
- **核心能力**:
  - 安全规则分发
  - GitOps 管理
  - SARIF 输出
- **优势**:
  - 企业级管理
  - 规则版本控制
- **劣势**:
  - **仅安全规则**
  - **无业务语义**
  - **无架构约束**

## 🔍 关键发现

### 现有工具的共性缺陷

| 维度 | 现有工具 | MetricGate 差异化 |
|-----|---------|------------------|
| **架构约束** | ❌ 仅有 ArchUnit(Java) | ✅ 语言无关的架构分层 |
| **增量检查** | ❌ 全量扫描 | ✅ 行级增量检查 |
| **LLM 友好** | ❌ 未优化 | ✅ 0 token、毫秒级 |
| **实时性** | ⚠️ 分钟级 | ✅ 毫秒级 |
| **本地化** | ⚠️ 多为 SaaS | ✅ 纯本地 |
| **业务语义** | ❌ 无 | ✅ 团队约束转化 |
| **自进化** | ❌ 静态规则 | ✅ 反馈驱动优化 |
| **成本** | ⚠️ Token 高 | ✅ 0 token |

### 市场空白点

1. **LLM 时代的代码约束层**
   - 现有工具都是为"人类开发者"设计
   - 没有考虑"AI 生成代码"的场景
   - **MetricGate 的机会**: 为 AI 生成的代码提供确定性验证

2. **团队非标约束的自动化工具**
   - 现有工具只有通用规则
   - 没有"业务约束→工具规则"的转化机制
   - **MetricGate 的机会**: 将团队的独特约束转化为可执行规则

3. **增量感知的架构检查**
   - ArchUnit 等需要完整编译
   - 无法检查未完成的代码
   - **MetricGate 的机会**: AST 级别的增量架构检查

4. **0 Token 成本的实时反馈**
   - 所有 AI 工具都需要 Token
   - 无法满足高频次、低延迟需求
   - **MetricGate 的机会**: 纯本地、零成本、毫秒级

## 💡 MetricGate 的定位

### 不是替代，而是补充

MetricGate **不是**要替代 SonarQube/golangci-lint 等传统工具，而是:

1. **填补空白**: 解决现有工具无法解决的问题
2. **快速反馈**: 在提交前提供即时反馈
3. **LLM 友好**: 专为 AI 生成代码设计
4. **团队定制**: 将独特约束转化为工具规则

### 与现有工具的协同

```
┌─────────────────────────────────────────────────────────┐
│                    Development Flow                       │
└─────────────────────────────────────────────────────────┘
                          ↓
        ┌──────────────────────────────────────┐
        │  Pre-commit Hook                      │
        │  • metricGate check -diff            │ ← 快速、增量、本地
        │  • 只检查新增行                        │
        └──────────────────────────────────────┘
                          ↓
        ┌──────────────────────────────────────┐
        │  CI Pipeline                           │
        │  • metricGate check (full)           │ ← 完整检查
        │  • golangci-lint run                 │ ← 深度静态分析
        │  • SonarQube analysis                │ ← 长期趋势
        │  • ArchUnit tests                    │ ← 架构验证
        └──────────────────────────────────────┘
                          ↓
        ┌──────────────────────────────────────┐
        │  Nightly/Batch                        │
        │  • SonarQube deep scan               │ ← 深度扫描
        │  • Security scanning                 │ ← 安全审计
        │  • Metrics aggregation               │ ← 趋势分析
        └──────────────────────────────────────┘
```

**各司其职，互不重叠**:
- **metricGate**: 实时、增量、架构、LLM 友好
- **golangci-lint**: 深度静态分析、类型检查
- **SonarQube**: 长期趋势、可视化、报告
- **ArchUnit**: 深度架构验证 (Java)

## 🎯 结论

### 1. **MetricGate 不是传统的 CI 工具**

它更准确的说法是:**"LLM 时代的确定性约束层"**

### 2. **现有工具没有完全覆盖类似功能**

- SonarQube/golangci-lint: 传统静态分析，无架构约束、无增量、无 LLM 优化
- ArchUnit: 仅 Java、需类型系统、无法检查未完成代码
- Policy Bot/Kodus: 审批流程控制，非代码质量检查

### 3. **MetricGate 的独特价值**

| 维度 | 现有工具 | MetricGate |
|-----|---------|-----------|
| **架构约束** | ⚠️ 有限 | ✅ 完整 |
| **增量检查** | ❌ 无 | ✅ 行级 |
| **LLM 场景** | ❌ 未优化 | ✅ 原生支持 |
| **实时反馈** | ⚠️ 慢 | ✅ 毫秒级 |
| **团队定制** | ❌ 通用规则 | ✅ 约束转化 |
| **成本** | ⚠️ Token 高 | ✅ 0 token |

## 📈 建议

### 短期策略

1. **强调差异化**: 不要与传统 linter 竞争，而是突出独特价值
2. **协同而非替代**: 明确与现有工具的互补关系
3. **从小处切入**: 先解决"架构约束 + 增量检查"这个痛点

### 长期愿景

1. **成为 LLM 时代的基础设施**: 所有 AI 生成代码的必经之路
2. **建立团队约束标准**: 让每个团队都能定义自己的约束
3. **构建约束生态**: 共享和复用约束模板
