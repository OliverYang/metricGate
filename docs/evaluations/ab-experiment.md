# LLM 约束效果 A/B 实验设计（下一步的核心验证）

目的：回答"确定性约束到底能不能改善 LLM 生成代码的质量与成本"——评估报告
(evaluation.md) 中唯一未验证的命题。本文件是
[docs/value-proof.md](../strategy/value-proof.md) 证据阶梯中的 **R2 一级**。

## 0. 先做基率预检（最便宜、最决定性，必须先做）

**先厘清一个常被混淆的点**：`evaluation.md` 的 150/150 检出率证明的是
**引擎正确实现了规则**，不是**方向有价值**。一个 100% 正确的检查器，如果模型
本来就不犯这类错，价值仍然是 0。

价值可分解为（见 value-proof.md §4）：

    价值 ≈ P(模型违反本仓库约束) × 每次拦截省下的返工 − 闸门成本(≈0)

P 是唯一没测过的项，也是决定一切的项。**所以在跑 A/B 之前，先花近乎为零的成本测 P**：

1. 取 N（≥20）个真实任务，裸生成（不给任何 metricgate 工具），产物落盘。
2. 离线跑 `metricgate check`，把违规**按类拆分**计数：
   banned-api / 分层与禁止边 / 签名对齐 / 依赖白名单 / 度量阈值。
3. 各类的基率即 P。

**判据**：某类 P ≥ 10–15% ⇒ 该类值得为它做工具；全类 P ≈ 0 ⇒ **停止该方向**。
**理由**：基率是乘法的左因子，接近 0 时后面所有实验的期望收益都接近 0，
不值得投入 A/B 的工程量。此步不需要改造 agent 协议，离线跑一遍即可。

**✅ 已完成（n=22）→ [`evaluation-base-rate.md`](evaluation-base-rate.md)。**
结果：ANY 违规 **31.8%**、error 级 **9.1%**、度量阈值类 **18.2%**、架构类 4.5%
（自然产生且编译器抓不到）、**API 幻觉 0/22（负结果）**。
⇒ 方向未被推翻，但 **R2 的任务集应加权到"算法自由度"与"跨包组合"两类**（基率所在）。

**✅ 补充已完成 → [`evaluation-reuse.md`](evaluation-reuse.md)（重造率，三臂消融）。**
API 幻觉 0/22 的真因不是协议不严，而是**编译器本身就是免费的确定性检查器** ——
agent 会 `go build` 并自修，编译错误活不到最后。改测编译器抓不到的"重造既有实现"后：
**指定位置+名称 ⇒ 0/10 复用（15 findings，含 3 error + 1 clone）；位置自由 ⇒ 5/5 复用（0 findings）。**

**这两份结果给 R2 的两条硬约束**：
1. **任务集必须同时包含两种框架**（"在包 P 新建函数 F" 与 "我需要 X，位置你定"），
   否则会系统性高估或低估工具价值。
2. **不要拿编译器已覆盖的类当卖点**（API 幻觉）。端点应落在编译器抓不到的三类：
   **度量阈值 / 架构分层 / 组织约定（禁用 API）**。

**✅ 追问已完成 → [`evaluation-prompt-vs-gate.md`](evaluation-prompt-vs-gate.md)（提示 vs 闸门）。**
在 Arm A 框架下只加**一句**复用提示：复用率 **0% → 80%**，findings **15 → 4**。
但残余失败**不都是"不听话"**（`clones.fingerprint` 未导出是真阻塞，
`arch.Check` 只是适配成本）；且**照提示复用后新引入 `model→selection` 边，触发 `sdp-violation`**。
⇒ **给 R2 的第三条硬约束**：
3. **A/B 的 B 臂必须把"提示"与"闸门"分开计**。提示只能改变**意图**，
   闸门才是**事实**（验证 + 暴露 API 缺口 + 抓全局后果）。二者混在一臂里会
   把提示的收益误记到工具头上。

**✅ 三个后续问题已完成 → [`evaluation-hint-and-cost.md`](evaluation-hint-and-cost.md)。**
含糊提示（Arm E）总分相同但**失败题目不同**，其中一次是"注释里点名了 `internal/repomap`
仍然重写" —— 这正是闸门不可替代的直接证据；
**"省探索"这个价值点被证伪**（不用工具也能 5/5 复用）；
SDP 冲突的成因是**本仓库层声明漏了 6 个包**，已按"消息给修法 + 严重度低于 `fail_on`
+ `sdp_tolerance` + `sdp: off`"调和并逐项验证。

## 实验设计

**变量**：同一个 LLM + 同一组任务，两组 prompt 环境。

- A 组（对照）：裸生成。只给任务描述 + 目标文件路径。
- B 组（实验）：约束环境。MCP 工具可用（get_constraints / check_code /
  list_stubs），系统指令要求"生成前先 get_constraints，每次编辑后 check_code，
  全绿才算完成"。

**任务集**（每组相同的 10 个任务，隔离运行）：

1. 3 个"对齐既有接口"任务：给定仓库中已存在的 interface，生成新的实现类/结构体
   —— 度量是否复用了既有符号（**不再度量 API 幻觉率**，见下方口径修正）
2. 3 个"修改既有文件"任务：往真实仓库的文件里加函数
   —— 主要度量是否遵守该仓库 policy（禁用 API、错误处理）
3. 2 个"生成完整 service"任务（复用 v3 打样场景）
4. 2 个"填空"任务：把 list_stubs 找出的桩补全

**度量指标**（每个任务自动采集）：

| 指标 | 采集方式 | A 组 | B 组 |
|---|---|---|---|
| 编译通过 | `go build ./...`（**只作噪声过滤，不作端点**） | 必采 | 必采 |
| **违规数（按类）** | 产物统一过 `metricgate check`（A 组**不**把结果回传给模型——仅离线量化违规率；B 组在会话内已 check 过），按 A/B/C/D 分类统计 | 必采 | 必采 |
| 一次通过率 | 产物首次过 `metricgate check`（0 error 0 warning）的比例；B 组需在工具返回全绿后才算完成 | 必采 | 必采 |
| 返工轮次 | 编译失败/符号不存在导致的返工轮数（会话日志统计） | 必采 | 必采 |
| 返工 token | 每任务总 token（会话日志）；B 组额外计入工具调用 token（≈0） | 必采 | 必采 |
| 墙钟时间 | 每任务耗时 | 必采 | 必采 |
| 人工评分 | 产物可读性/正确性 1-5 分（盲评，打乱 A/B） | 必采 | 必采 |

**首要指标口径（两次修正，最终以此为准）**：

1. ~~API 幻觉率~~ —— **已被 R1 推翻**（0/22，见 `evaluation-base-rate.md` §4.4）。
   原因是结构性的：**编译器本身就是免费的确定性检查器**，agent 会 `go build` 并自修，
   编译错误活不到最后。拿它当端点必然测出 0。此指标降级为噪声过滤。
2. 主指标用 **每千 token 的"违规避免数"**
   （= (A 组违规率 − B 组违规率) × 任务规模 ÷ 每任务 token），而非一次通过率。
   原因：一次通过率被任务难度与模型自纠混淆；而本产品的价值主张本身是经济性的
   （省 token / 省返工轮次），端点就该是经济性的。一次通过率降为次要指标保留。
   **端点必须落在编译器抓不到的地方**：度量阈值 / 架构分层 / 组织约定 / 重造。

**误报率（独立门槛指标）**：B 组工具报出的 findings 中，被 agent 判定为
误报（或明确不改）的比例。基率高但误报也高 ⇒ agent 学会忽略 ⇒ 实验反而变差。
此项不并入"违规数"，单独统计。

## 消融实验（不能只测"全工具 vs 无工具"）

只做二组对照，无法回答**该往哪个触点投钱**。必须拆成四臂，同一批任务：

| 臂 | get_constraints（生成前） | check_code（生成后） | 回答什么 |
|---|:--:|:--:|---|
| A 对照 | ✗ | ✗ | 基线 |
| B1 | ✓ | ✗ | 仅"生成前约束"值多少 |
| B2 | ✗ | ✓ | 仅"生成后校验"值多少 |
| B3 | ✓ | ✓ | 两者是否互补（超可加） |

**决策含义**：若 B2 ≈ B3（生成后校验吃掉全部收益），则 `get_constraints` /
context pack 这条产品线**应当被削减或降级**；若 B1 显著而 B2 不显著，则重心
应放在"喂约束"而非"查代码"。这是实验该产出的**投资分配**结论，不只是方向对错。

## 判定标准

- **采纳**：一次通过率显著提升 或 返工 token 下降 >30%，且墙钟时间不劣化 >10%
- **调整**：约束有效但 check_code 打断节奏（agent 过度调用）→ 调整触发策略
- **放弃信号**：两组无显著差异且 B 组显著更慢 → 重新审视定位

## 已知风险

- agent 对工具的遵从度依赖系统提示词质量（两组都要写清楚任务，B 组额外写工具协议）
- 结果受所选 LLM 影响大 → 至少跑两个模型家族
- 任务集偏向结构约束可判的问题（这是设计意图，但结论外推要克制）

## 什么会推翻这个方向（预先登记，避免事后找理由）

| 观测 | 结论 | 动作 |
|---|---|---|
| 所有类别基率 P < 5% | 模型在这些约束上几乎不犯错 | **停止**该方向，不要做 A/B |
| B 组一次通过率提升 < 5pp 且 token 未降 | 闭环价值不成立 | 放弃"约束层"定位，重新审视 |
| B 组误报被 agent 忽略（调用后不修） | 反馈是噪音 | 先修误报率，再谈价值 |
| agent 每任务工具调用 < 1 次 | 通道是理论的 | 定位问题在接入形态，不在引擎 |
| B 组显著更慢且无质量提升 | 打断节奏 | 调整触发策略（异步 / 批量） |

**注**：能力类证据（"模型会犯 X 错"）随模型变强而衰减，所有此类数据必须标注
模型版本与日期；知识类证据（"本仓库约束不在权重里"）不衰减，是长期主线。
完整阶梯见 [value-proof.md](../strategy/value-proof.md) §5。
