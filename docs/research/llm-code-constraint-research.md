# 约束/优化 LLM 生成代码：论文方向调研（2026-09）

> 背景与问题：旧研发模式下"规约"来自团队规范文档（见 `docs/pilot/` 试点）。在 LLM 代理研发模式下，

> 结论先行：**9 个方向中，采纳 4（修复回路、guardrails、质量退化度量、仓库接地已有）、改编 2（候选排序、混合评审）、

## 方向 1：静态分析反馈修复回路（gate-in-the-loop）—— **采纳，核心**

**论文**：
- InferFix（arxiv 2303.07263，Microsoft/Meta）：Infer 静态分析器 + LLM 端到端修复，检索相似历史告警修复作为 few-shot，已在生产部署。
- Self-Debug（arxiv 2304.05128，Google）：模型自调试；反馈形式包括代码解释、单元测试、编译/运行错误——证明"结构化反馈进 prompt"能显著提升收敛率。
- Helping LLMs Improve Code Generation Using Feedback from Testing and Static Analysis（arxiv 2412.14841）：测试 + 静态分析双通道反馈回路。
- CodeCureAgent（arxiv 2509.11787）：对静态分析告警做分类 + 修复的 agent 化流水线。
- PredicateFix（arxiv 2503.12205）：用"桥接谓词"修复静态分析告警（在告警点插入谓词表达式即修复）。
- LLM-Based Repair of Static Nullability Errors（arxiv 2507.20674，Meta）：百万行级代码库上用 LLM 修复可空性静态错误的工业实践。

**核心思想**：不要指望 LLM 一次生成正确代码；把**确定性分析器的结构化输出**（规则、位置、原因）作为反馈喂回生成循环，直到告警清零。

**metricGate 映射**：metricGate 的 findings（RuleID/File/StartLine/Message，含 JSON 输出）正是该回路所需的反馈通道——零改动已兼容。差距在"回路"本身：目前 agent 需自己调 `check_code`/`check_path`；没有"修到干净为止"的自动循环（这是 agent 框架侧的职责，metricGate 提供闸门即可）。

**工程成本**：低（已有）。**决策：采纳**。后续 R2 实验：A/B 对比"带 metricgate 反馈回路"与"无反馈"的修复收敛率。

## 方向 2：执行无关的候选重排序（best-of-N reranking）—— **改编（P1）**

**论文**：
- Coder[Reviewer]（ICML 2023，proceedings.mlr.press/v202/zhang23av）：用模型自身似然对 N 个候选重排序，发现**模型似然偏好退化解**——必须引入外部判别器。
- Sifting through the Chaff（arxiv 2408.13976）：利用执行反馈对候选排序（需要跑测试/执行）。
- edis-code-bestofn（gitlab.com/fars-a/edis-code-bestofn）：best-of-N + 判别器的工程实现参考。

**核心思想**：生成 N 个候选后，用执行或**执行无关的判别器**挑最好的。执行判别贵且慢；静态判别（确定性）免费。

**metricGate 映射**：metricGate 是天然的**确定性无执行判别器**：N 个候选各跑一次 `check`，按 findings 数/严重度/风险分排序。可做成 `check --rank f1.go f2.go ...` 或 MCP tool `rank_candidates`。

**工程成本**：中。**决策：改编，P1**（先落地记分卡，排序复用同一套计数）。

## 方向 3：API/包幻觉防护 —— **已采纳（unknown-dependency），P2 增强**

**论文**：
- We Have a Package for You!（arxiv 2406.10279，USENIX Security 2025）：LLM 生成代码中大量引用**不存在的包**（包幻觉），并催生 slopsquatting（抢注幻觉包名投毒）攻击面。
- Towards Mitigating API Hallucination in Code Generated by LLMs with Hierarchical Dependency Aware（FSE 2025，dl.acm.org/doi/10.1145/3696630.3728569）：层级依赖感知缓解 API 幻觉。
- 相关：AAAI 34717、arxiv 2401.01701、2408.08333、2409.20550。

**核心思想**：幻觉 API/包在**依赖清单层面**必然露馅——import 了不存在的包/依赖，静态可查。

**metricGate 映射**：`unknown-dependency` 规则（允许清单外 import 即告警）已实现并经 Java 试点验证（45 个 test-scope 误报修正后可用）。P2 增强：对照 pom.xml/go.mod 的**依赖清单校验**（deps scan），把"允许清单"从手工维护变为从清单生成。

**工程成本**：已有；增强成本低。**决策：已采纳，P2 增强**。

## 方向 4：语法/类型受限解码（constrained decoding）—— **拒绝（当前形态）**

**论文**：
- Flexible and Efficient Grammar-Constrained Decoding（arxiv 2502.05111）；Parser Stack Classification（arxiv 2608.03065）；GCD without Finetuning（arxiv 2305.13971，EMNLP 2023）；Learning CFGs via Declarative Agentic Programming（arxiv 2608.05493）。
- 反例：Grammar-Constrained Decoding Can Jailbreak LLMs into Generating Malicious Code（arxiv 2606.11817）——语法约束反而可能提高恶意代码生成率。

**核心思想**：在解码时用 CFG/类型系统约束 token 空间，让语法/类型错误从源头不可能出现。

**拒绝理由**：需要进入推理栈（自研推理/改采样），与 metricGate "模型无关、本地、确定性闸门"的定位冲突；且约束语法不等于约束语义，还可能引入 2606.11817 所示的反效果。**闸门（解码后检查）+ 提示（解码前约束）已覆盖其实际收益**。

## 方向 5：形式规约/验证生成 —— **思想采纳**

**论文**：
- SpecGen（arxiv 2401.08807，ASE 2024）：LLM 自动生成形式化程序规约。
- ClassInvGen（arxiv 2502.18917，Microsoft）：LLM 合成类不变式。
- Clover（arxiv 2310.17807）：闭环可验证代码生成（生成→验证→修复）。
- AlphaVerus（arxiv 2412.06176）：自举式形式验证代码生成（Treefinishment）。
- 其他：P³（2608.09277）、VERINA 基准（2505.23135）、VeriContest（2605.08553）、SpecEval（2409.12866）、ICST 2025 SAFE-ML 工作坊论文（2608.13077）。

**核心思想**：先用 LLM 从自然语言生成**机器可查的规约**，再让代码生成受规约约束、由证明器/验证器闭环。

**metricGate 映射**：policy.yaml 本质就是"轻量规约"——确定性可查的那部分契约。试点的"规范文档 → policy 转化 + 人审"流程即该思想的低成本落地。重型验证（Dafny/证明器）不进路线图。

**工程成本**：试点流程已有。**决策：思想采纳**。

## 方向 6：仓库级检索接地 —— **已有（context pack / repomap / MCP）**

**论文**：RepoCoder（arxiv 2303.12570，EMNLP 2023，迭代检索-生成）；CodePlan（arxiv 2309.12499，Microsoft，仓库级多文件编辑规划）。

**metricGate 映射**：`getRepoMap`/`getConstraints`/`findSymbols`/`getImpact`/context pack 已构成确定性接地上下文。本地 R1b 实验证实接地决定重造率：指定包+函数名 → 0% 重造；放开不指定 → 100% 重造。

**工程成本**：0（已有）。**决策：已有**，继续做 token 预算控制即可。

## 方向 7：确定性 guardrails / policy-as-code —— **采纳（本期 agentic 档）**

**论文**：NeMo Guardrails（arxiv 2310.10501，NVIDIA）：可编程的确定性"护栏"层，夹在用户/模型之间拦截越轨行为；rails 与模型解耦。

**metricGate 映射**：policy.yaml 即代码层的 rails；**agentic preset = "agent 研发模式"的 rail 集**（放宽风格类阈值、收紧边界类严重度）。本期强化：todo/伪完成标记升级为 warning（LLM 留 TODO = 未完成信号）、unknown-dependency/empty-block 保持 error、Note 说明档位意图。

**工程成本**：低。**决策：采纳，本期实现**。

## 方向 8：AI 代码质量退化的度量证据 —— **采纳（记分卡的依据）**

**报告**：GitClear《AI Copilot Code Quality》2025（gitclear.com/ai_assistant_code_quality_2025_research；正文需订阅，数字转引自 kracekumar.com/post/ai_copilot_code_quality_paper/ 摘要）：
- 2024 年首次出现 **Copy/Pasted 行数超过 Moved 行数**（Moved 强烈暗示重构活动在萎缩）；
- copy/paste 行数增速比 GitClear 2024 年预测**快 6%**；含重复代码块的 commit 占比增长更快；
- 缺陷率随 AI 采用上升（2024 年 10 月发布的数据证实其此前预测）；
- 基于 2.11 亿行变更代码 + 36,894 名开发者调查（开发者诉求是"更多代码、更快"）。

**metricGate 映射**：这些退化维度（复制粘贴↑、重构↓、缺陷↑）恰好对应已有能力：function-clone/near-clone（复制粘贴）、churn 与 regress（重构与回归）。**记分卡把"LLM 改动是否制造克隆/回归"纳入同一视图**，让团队可以用数字回答"AI 代码质量"问题，而不是凭感觉。

**工程成本**：低（记分卡聚合既有计数）。**决策：采纳，本期实现**。

## 方向 9：混合静态分析 + LLM 评审 —— **改编（bundle 已有雏形）**

**论文**：
- CodeReviewer（arxiv 2203.09095，Microsoft）：面向自动化代码评审的预训练模型。
- Combining Large Language Models with Static Analyzers for Code Review Generation（arxiv 2502.06633）：**把静态分析器输出作为 LLM 评审的结构化输入**，显著提升评审质量——方向与 metricGate `get_review_bundle`/`bundle` 完全一致。

**metricGate 映射**：bundle 已把 findings/度量/影响面打包给评审 agent。记分卡可作为 bundle 的摘要页（P1）。

**工程成本**：已有雏形。**决策：改编，P1 接入**。

## 本地实证（与方向互证）

来自 `docs/evaluations/`（R1/R1b 实验，22 任务、本仓库）：
- **度量阈值（C 类）是 LLM 代码最高产违规源**：18.2% 任务产生 error 级度量违规——旧 lint 不管、LLM 系统性偏差，验证方向 7"放宽风格、收紧边界"的档位设计。
- **重造率由接地决定**：指定包+函数名 → 0% 重造；放开 → 100%。验证方向 6。
- **一句提示 vs 闸门**：提示把重造从 10/10 降到 2/10，残余 2 例是提示结构性做不到的（闸门可查）。证明方向 7 的"闸门兜底"必要性。
- **API 幻觉在本仓库为 0**（R1 负结果）——但文献（2406.10279）表明外部依赖越多风险越大，`unknown-dependency` 作为廉价保险仍然保留。

## 边界（诚实声明）

纯语义正确性（"这段逻辑对不对"）静态不可查——本调研所有方向都不解决它；能落地的是**结构性、边界性、完备性**约束：架构边界、依赖合法性、度量回归、克隆、伪完成标记、影响面。这与 `docs/claims.md` 的能力边界声明一致。
