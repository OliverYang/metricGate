# metricGate Audit Cockpit 产品验收报告

- **验收人角色**：项目经理（纯产品视角，不看设计与开发文档）
- **验收对象**：本地服务 `http://127.0.0.1:8787/`（`metricgate cockpit serve`）
- **验收方式**：黑盒驱动真实数据。**已用真实浏览器（arm64 原生 headless Chrome + CDP）逐屏走查并截图**（截图存 `/tmp/review/out/`）。补充说明：本机 headless Chrome 之前起不来，根因是 `/Applications/Google Chrome.app` 是 universal binary 但被默认跑成 x86_64 走 Rosetta 转译，`--headless=new` 下 CDP 端口不监听、`--dump-dom` 挂起；解法是 `arch -arm64 <Chrome>` 原生运行（仓内截图批次 `scripts/cockpit-observe.sh shots` 全挂也是同因）。**已修复**：给截图 runner `/tmp/shots/cdp_shoot.mjs` 加了 darwin+arm64 自动探测，用 `/usr/bin/arch -arm64` 启动 Chrome，实测 3 张图 2.7s 全部成功（旧行为 13s+/张且全挂）。注意：本机是 Apple Silicon（`sysctl hw.optional.arm64=1`），但整个工具链（node/brew）跑在 x86_64+Rosetta 下（`uname -m=x86_64`），故需 `arch -arm64` 显式拉回原生。另用 `internal/cockpit/web/smoke.mjs` + 自建渲染 harness 以真实 Go handler payload 交叉验证。
- **数据快照**：7 个识别项目、370 条调用记录（仅 154 条 ≈ 41.6% 能归属到项目，216 条未归属）、53 条活跃运行、约 33.6 万个 issue（此为 history.db 存量，由 harness 以真实 payload 渲染得到；**线上 `/api/issues` 因超时实际返回 0 条**，见 P0）；`.metricgate/history.db` 已达 **2.1GB（2291806208 字节）**。

## 一、验收结论

服务能启动、9 个视图都能渲染出真实数据、路由/面包屑/刷新/弹窗/键盘方向键等基础交互可用，**工程质量不低**。但从产品角度存在**一个系统性问题**和若干**自相矛盾的呈现**，直接影响"能不能信这个工具"：

> **系统性问题：作用域（scope）隔离在多个视图失效。** 进入"bugbye-miserver"等项目后，看到的调用、策略、度量数据并不是该项目的，而是 metricGate 自己的。用户点进任何项目，都得到一份和项目无关、和其它项目雷同的看板。这会让"多项目审计驾驶舱"的核心卖点落空——所有项目看起来都一样。

**总体评价：功能骨架齐全，但当前有两条阻断级问题——问题分诊接口在真实浏览器里超时（整页空），作用域隔离失效（进项目看到 metricGate 的数据）。门禁又存在 go/java 同值、状态列不区分 warning/error 等自相矛盾。建议先修迭代 1（接口可用性 + 作用域隔离）和迭代 2（门禁矛盾）再对外。**

## 二、全流程走查发现（按严重度分级）

### P0 — 阻断性：问题分诊页数据接口超时，整页在真实浏览器里是死的

**真实浏览器实测**（`arch -arm64` Chrome，非 harness 模拟）：
- 打开 `#/view=issues`，页面渲染出筛选栏（严重度/状态/规则均"暂无数据"）、`0 个问题 第 1 / 1 页`、`没有匹配的问题`。截图 `11-issues-8899.png`。
- 根因：`/api/issues` 端点**每次 30 秒超时、返回 0 字节、连接被中断**（`curl … code=000 time=30.0s`，连 `limit=1` 也超时）。而 `/api/dashboard`(20MB)、`/api/gate`、`/api/policy`、`/api/measures` 均 200 正常。
- 数据侧原因：`.metricgate/history.db` 已膨胀到 **2.1GB**，issues 查询在默认窗口（last 60 runs）下无法在超时前完成。

**为什么是 P0**：问题分诊是产品核心动作之一（"跨运行去重后的问题列表，可逐个流转状态"）。接口稳定超时 = 用户点进去永远看到空列表，等于该功能不存在。这比之前判断的"33 万条无收敛引导"严重得多——**当前根本没有 33 万条可翻，是 0 条**。

**修复状态（迭代 1 收口，2026-10-16）**：✅ **已修复**。根因是 `internal/store/issues_query.go` 的候选查询从不把 `Window.Limit` 下推进 SQL，每次对全库 1,172,857 行 findings 做 10 列 GROUP BY。修复后同库对照：`code=000 time=37.03s` → **`code=200 time=2.86s`（≈13×）**，真实浏览器分诊页能出 41 条 bugbye 问题。残留：`scope=unassigned` 8.10s、`?limit=500` 34.09s（记迭代 2）。见 `docs/iterations/cockpit-ui/iter-05-p0-availability-and-scope.md` §8。

**修复方向**：(1) issues 查询加索引/游标分页，避免全窗口扫描；(2) history.db 归档或分表，控制单库体积；(3) 前端对慢接口要有"加载中/超时重试"态而非静默空态（当前无任何错误提示，用户无法区分"没问题"和"接口挂了"）。—— **(1)(3) 已在迭代 1 完成；(2) 仍开放（设计文档 §13 开放问题 3）。**

### P0 — 阻断性：作用域（scope）隔离失效，进项目 = 看错数据（真实浏览器截图确认）

| 现象 | 证据（真实数据渲染） |
|---|---|
| 进项目后"调用轨迹"恒为空 | 真实浏览器截图 `22-calls-bugbye`：bugbye 项目内 `calls` 视图 `LOCAL TRACE 调用轨迹 0 条 … 没有匹配的调用记录`。而全局 `calls` 有 370 条。根因：这 370 条几乎都属于 metricGate 自己，bugbye 等项目 0 条归属调用。 |
| 进项目后"扫描配置"显示的是 metricGate 的策略 | 真实浏览器截图 `21-policy-bugbye`：bugbye 项目内 `policy` 视图显示 `路径 /Users/mac/Downloads/metricGate/.metricgate.yaml`，面包屑还停留在"未归属记录"。`curl "/api/policy?scope=bugbye-miserver"` 返回的 `root` 仍是 `/Users/mac/Downloads/metricGate` —— 后端硬编码返回本机这一份，不接 scope 参数。 |
| 进项目后"项目概览"是全局门禁结果 + 全局度量 | 真实浏览器截图 `23-overview-bugbye`：bugbye 概览顶部直接是全局的 `✕ FAILED 运行 #1233` + 9 项度量（Cyclomatic 1112 等），调用总数/质量运行全是 0/—。即项目概览展示的是全局聚合，不是该项目。 |

**为什么是 P0**：产品主页是"项目总览 → 点进某项目"，这是用户第一动作。进项目看到的是别人的数据、策略、调用，属于"看到的内容与所选对象无关"，是信任崩塌级缺陷。

**修复状态（迭代 1 收口，2026-10-16）**：✅ **后端已修复**。`/api/policy` 现在接受 `?scope=`：`root` 随之变化（无 scope→`/Users/mac/Downloads/metricGate`；`scope=bugbye-miserver`→`/Users/mac/Downloads/main/bugbye-miserver`；**`scope=/etc`→400 unknown scope**）。gate/measures/issues 同样按 scope 取数（gate 运行号 `all`#1270 / `unassigned`#1260 / `bugbye`**#961**；issues total 37543 vs **41**）。真实浏览器 bugbye 概览度量 Cyclomatic 7（全局 1112）、门禁徽标 `✓ PASSED 运行 #961`。残留：调用归属识别率仍是 51.8%（本迭代只做"诚实呈现"，不做回填追认）；calls 视图为 0 条属真实情况，已在界面标注未归属计数。见 §8。

**修复方向**：calls/runs/overview 的 scope 过滤要真正生效（`projectOf(s)`/`callsInScope` 已按 `p.root === scope` 匹配，但归属识别只覆盖 41.6%，需补齐 `projectRoot` 回填）；`/api/policy` 需支持按 scope 返回该项目的策略，或把"扫描配置"从 workspace 视图移到全局单例视图。—— **`/api/policy` 接 scope 已完成；归属回填不做（改为诚实标注）。**

### P1 — 门禁页自相矛盾：判定 PASSED 却列出"发现问题"

`gate` 视图真实文本：
```
✓ PASSED  no findings at or above the fail_on level
...
File length   ≤ 800   实测 2560   超出 1760   发现问题
Fan-out       ≤ 10    实测 17     超出 7      发现问题
```
- **矛盾 1**：顶部大徽标与条件表状态列不匹配。真实浏览器截图 `20-gate-global`：徽标 `✕ FAILED 6 errors at or above fail_on=error`，但下方 go/java 条件表的状态列**只有"通过 / 发现问题"两态，不区分 warning 与 error**——用户看不出到底是哪 6 行触发了 error 级失败（表里 File length、Cyclomatic 等一堆都标"发现问题"，但哪几个算 error 无从判断）。早期 harness 快照里还出现过徽标 `✓ PASSED` 与同屏 2 行"发现问题"并置的情况（`fail_on=error`、那两项是 warning 级，逻辑上该 PASSED，但呈现上矛盾）。
- **矛盾 2**：`go` 与 `java` 两个语言块，9 项度量阈值与实测值**完全相同**（真实浏览器：Cyclomatic 1112、File length 298040、Function length 12209、NPATH 9216、Fan-out 20…两语言块一字不差）。真实仓库里 Go 和 Java 不可能数字一致，确认是把同一份度量结果复制到了多个语言块。

**修复方向**：徽标需反映"有 N 项超阈但未达 fail_on"的中态；语言块需按真实语言分别取数。

### P1 — 问题分诊页：接口超时（见 P0）+ 数据陈旧 + 海量无处理

> 补充：真实浏览器里 issues 页当前因 `/api/issues` 超时而显示 0 条（见上文 P0）。以下是**接口恢复后**仍存在的呈现问题（来自 harness 以真实 payload 渲染的快照）。

- `issues` 视图：`335864 个问题 第 1 / 6718 页`，且范围行 `范围：last 60 run(s) (architecture)` 指向陈旧路径 `.data/m2b-raw/...`。
- 顶部分组计数自相矛盾：`Error 77492 / Info 5910 / Warning 252462`，但"状态"栏 `未处理 335862` 与总数 335864 差 2（= 已接受 2），这个对得上；问题在于**没有任何"如何处理 33 万条"的引导**，6718 页翻页在产品上等于不可用。
- 每条 issue 同时罗列 `未处理 已确认 误报 已接受` 四个状态按钮，无默认选中高亮，用户不知道当前是哪个状态。

**修复方向**：默认按 run 或按规则收敛，提供"只看新增/只看本项目"的入口；状态按钮需显示当前态。

### P2 — "全局运行历史"其实是"未归属运行"，标题误导

`runs` 视图在全局作用域标题写 `RUN HISTORY 活跃运行`，但副文案是 `这些运行缺少项目路径，无法可靠地归入某个项目，因此单独列在这里`。也就是说**全局 runs 页展示的是"无主运行"**，而带项目的运行只在各自项目里。用户从"质量运行"进全局页，预期看到全部运行，实际只看到未归属的那批。

**修复方向**：全局页应合并展示"所有项目 + 未归属"（`scopeAggregate` 已有合并逻辑，但视图没用上），或把标题改为"未归属运行"。

### P2 — 项目总览对"空项目"无差异化，进空项目是死路

`projects` 总览：7 个项目里 6 个 `0 次调用`，只有 metricGate 有 154 次。每个项目卡片长得一样，点进空项目后看到的是空调用页 + metricGate 的策略（见 P0）。对纯运行型项目（有 runs 无 calls）没有任何提示告诉用户"这个项目只有质量运行数据，没有工具调用"。

**修复方向**：项目卡片区分"有调用 / 仅运行 / 空"；空项目落地页给可操作的下一步（查看运行、查看问题）。

### P2 — 空项目落地页顶部是全局 FAILED 门禁（真实浏览器确认）

真实浏览器进 bugbye 项目概览（截图 `23-overview-bugbye`）：该页顶部直接展示全局的 `✕ FAILED 6 errors at or above fail_on=error 运行 #1233` + 9 项度量，而该项目自身"质量运行 = 0"。即**一个 0 运行的项目，首屏看到的却是一次全局 FAILED 门禁和 1112 等全局度量值**，是本项目 scope 未生效（见 P0）在概览页的具体表现，同时构成对空项目的强误导。

**修复方向**：项目概览的门禁/度量严格取该项目 scope；无运行时应显式显示"该项目暂无质量运行"空态，而非回退到全局结果。

### P2 — 规则页自我声明"半成品"

`rules` 视图顶部大段说明：`本页当前显示生效的配置键，不是规则目录 … 缺列的本身就是发现项`，只列出 138 个配置键（如 `architecture.cycles`、`gate.fail_on`），没有规则的存在理由、参数、激活位置、历史 issue 数。作为"规则"入口，用户要的规则目录不在这里。

**修复方向**：接入 `/api/rules` 出口补齐规则目录列；在此之前至少在导航上把入口名从"规则"改为"生效配置键"，避免误导。

### P3 — 交互与文案细节

1. **时间戳不统一**：运行列表用 `2026/10/16 08:32:53`，时间线用 `22 分钟前`/`1 小时前`，度量实验用 `10-16T00:04`。同一份数据三种时间格式，跨页对比困难。
2. **运行编号 vs 提交号**：运行卡片主标识是 `#1225`，旁边跟提交 `5c1595c`，但几十条运行共享同一提交号时无法区分，缺少"这是什么操作触发的"（命令/路径）。
3. **门禁 meta  provenance 行**：`提交 5c1595c 10/16/2026…` 用本地时区，而 payload 是 UTC（`2026-10-15T04:37:52Z`），存在时区偏移展示，跨时区用户会误判。
4. **错误态不可见路径**：`check_code … ERROR` 的调用在 calls 页结论列只显示 `ERROR`，无 tooltip 说明错误内容，点"详情"才能看。
5. **无空态引导的度量实验**：`METRIC EXPERIMENT` 表格直接铺 20 行原始运行号，无"这个实验在测什么、结论是什么"的摘要。

## 三、交互 / 跳转 / 风格专项

- **跳转**：hash 路由（`#/view=…&scope=…`）完整，可分享；面包屑在项目内有"返回项目总览"，全局页正确隐藏。方向键可在 issues 列表移动选择。这些是达标的。
- **刷新**：读取中禁用按钮 + "读取本地数据…"提示已接线（`refreshBtn.disabled`、`updatedAt` loading 态），慢数据不会像卡死。
- **弹窗**：issue 详情 / 调用详情用 modal，含源码窗口（`/api/source`），但 smoke 断言暴露 `issue.select: the code window rendered no lines`——**源码窗口在真实数据下渲染不出代码行**，需复查（可能是所选 issue 的 fingerprint 未命中 `/api/source`）。
- **风格**：深色驾驶舱、卡片、徽标（PASSED/发现问题）、面包屑一致性好；主要风格问题不在视觉而在**语义一致性**（同一数字多处不同含义、同一状态两种写法），已归入 P1/P2。

### 状态与可编辑性模型（真实浏览器实测，反交底引用）

- **问题状态默认即可流转**：`状态`按钮行（`未处理/已确认/误报/已接受`）默认**可点击**，无任何"保存"或"应用"二次确认。用户误触即改变状态，且界面**无任何确认提示/撤销入口**（未观测到 undo/toast）。对高频误触的高风险操作，缺少防呆。
- **配置保存先自检后落盘**：扫描配置页 `保存配置` 按钮在成功保存后会**串行触发一轮 `gate`/`measure` 自检**（真实浏览器观测到保存后连续请求 `/api/gate` 再 `/api/measures`），而非仅写盘。
- **配置字段本地校验**：如 `gate.fail_on` 被输入非法值时显示"请填写 error|warning|info"；`languages.go` 等下拉切换后保存，**旧值不会回读**（保存后重新渲染仍显示默认值），存在"保存了但没生效/没回显"的观感问题。

### 导航与信息架构（真实浏览器实测）

- **左侧双分组导航**：工作区=`项目总览/项目概览/问题分诊/质量门禁/工具活动/质量运行`；审计记录=`规则/活动/扫描配置`。
- **面包屑语义错位（新发现）**：真实浏览器进 `bugbye-miserver` 项目后，面包屑显示 **`项目总览 › 未归属记录`**——但实际 scope 是 bugbye 这个仓库。即项目内页面被统一标成了"未归属记录"，与"进入的是某个项目"矛盾，进一步坐实 scope 隔离/归属识别失效（见 P0）。
- **项目卡静态指标**：`154 次调用 · 48 次未通过 · 最近活动`。

### 度量色阶与含义混淆（真实浏览器实测，建议修正）

- **CCG 等级 A–F 与 badge 数字非同一事物**：项目概览 `CCG C 25 warn 15 · err 25`，字母 C 是汇总等级，`warn 15` 是**度量实验触发的警告数**，`err 25` 是**策略规定的上限**，三者含义不同却并排，易误读为同一指标的不同阈值。建议在视觉与文案上区分"评级""实测触发数""策略上限"。
- **带宽度量显示 0 却列超阈**：`Fan-out C 20 warn 10 · err 0`，`err 0` 应表示"该度量无 error 级上限"，但与同列其它度量的 error 上限数字并排，看起来像"超阈 0 处"，语义冲突。

## 四、修改迭代排期

> 排期假设：1 名前端 + 1 名后端，按"先恢复信任、再补引导、后打磨"的顺序。每轮结束跑 `bash scripts/cockpit-observe.sh fast` 收口。

### 迭代 1 — 恢复可用性（P0，最高优先，约 5–6 人日）
> **状态：✅ 已完成并收口（2026-10-16）。** 落地子方案与逐条验收证据：`docs/iterations/cockpit-ui/iter-05-p0-availability-and-scope.md`（§4 改动点、§8 收口记录）。D1 九条：7 条通过、1 条通过但带残留（D1-1 的 unassigned/limit=500）、1 条通过（D1-9 的 2 条 error 级 finding 不属本迭代改动行）。

**目标**：核心页不再空/不再看错数据。

- T1.0 后端（新增，最阻断）：修复 `/api/issues` 超时——查询加索引/游标分页，避免 2.1GB history.db 全窗口扫描；控制单库体积（归档/分表）。前端对慢接口加"加载中/超时重试"态，不再静默空态。（后端 2d + 前端 0.5d）
- T1.1 后端：`/api/policy` 支持 scope，返回所选项目的策略；项目无策略时诚实回"未发现"。（后端 1d）
- T1.2 后端：补齐调用归属——把 `projectRoot` 回填逻辑覆盖到历史调用，或对无法归属的调用在项目内明确标注"这些是未归属记录"而非显示 0。（后端 1d）
- T1.3 前端：项目内 overview 的度量实验/趋势严格按 scope 取数，杜绝全局序列混入。（前端 0.5d）
- T1.4 回归：9 视图 × 3 作用域 smoke 全绿 + `cockpit-observe.sh fast`；补上真实浏览器（arm64 Chrome）回验 issues 页不再空。（0.5d）
- T1.5 面包屑与项目态：修正项目内面包屑把任意项目显示为"未归属记录"的问题（项目 scope 走查一遍，标题/crumb 与所选对象一致）。（前端 0.5d）
- T1.6 状态防呆 + 配置保存回显：问题状态流转加二次确认/撤销；修复配置字段保存后旧值不回读。（前端 0.5d）

**验收口径**：(a) 问题分诊页能出数据、不再 30s 超时；(b) 进 bugbye 项目，calls/policy/overview 三者要么是该项目数据，要么明确标注"无/未归属"，绝不出现 metricGate 的数据。

### 迭代 2 — 消除自相矛盾（P1，约 3 人日）
**目标**：同一数字同一含义，同一状态一种写法。

- T2.1 门禁页：徽标三态（全通过/有超阈但未达 fail_on/未达 fail_on 失败）之外，条件表状态列需区分 warning 与 error，让用户看出是哪几行触发了 fail_on。（前端 1d）
- T2.2 门禁页：语言块按真实语言分别取数，消除 go/java 同值。（后端 0.5d）
- T2.3 issues 页：状态按钮显示当前态；范围行指向的陈旧 `.data/` 路径改为人类可读的当前范围。（前端 1d）
- T2.4 源码窗口：修复真实数据下 `/api/source` 渲染不出代码行的问题。（前端 0.5d）

**迭代1 收口新暴露的残留（已实测，一并排进本轮）**：
- T2.5 错误态与计数不再自相矛盾：超时/失败时不再同屏显示"0 个问题 / 第 1 / 1 页 / 暂无数据"（错误卡说读不到、标题说是 0 个），改为把计数行与 facet 降级为"—"。（前端 0.25d）
- T2.6 服务端错误正文透出：非法 scope 时前端显示服务端可读正文（`unknown scope: … (known projects: …)`）而不是通用"请求失败 (400)"。（前端 0.25d）
- T2.7 issues 候选查询的剩余热点：`scope=unassigned` 8.10s（该窗口 60 run 含 201,175 候选指纹）、`?limit=500` 34.09s——考虑候选计数缓存或限制可用 limit 上限。（后端 0.5d）
- T2.8 瞬时 500 复现与防护：取证中见过 1 次 `/api/issues` 500（服务端响应），6 路并发复测未复现，需加慢请求日志/保护以防隐性超时。（后端 0.5d）
- T2.9 侧栏数据源标签说谎：迭代1 收口后服务以 `-log` 启用调用日志，但**非 projects 视图的侧栏仍显示「日志未启用」**（真机 innerText 取证：`#view=runs`/`#view=issues`/`#view=rules` 均为「日志未启用」，只有 projects 页显示 `.metricgate/mcp-calls.jsonl`）。根因：`s.logPath` 只在 `fetchDashboard` 成功时赋值（app.js:539），而只有 projects/overview 会拉 dashboard（app.js:1154-1157 / :1707-1712）⇒ 深链到任意视图时底栏把「我没读到」渲染成「没有」。修法：logPath 与 dashboard 解耦（独立轻量端点或 `/api/spec` 带出），并在未取到时显示「未读取」而非「未启用」。（前端 0.25d）
- T2.10 顶栏时间戳同理：非 projects/overview 视图恒显示「**尚未同步**」（app.js:2846-2854 以 `state.dashboard?.generatedAt` 为唯一依据），但页面数据其实已经加载完（runs 页 53 条、issues 页 41 条都在屏上）。「尚未同步」与「已同步但不知道服务器生成时间」被压成同一个词，用户会以为整页是陈的。修法：各视图 fetch 成功后记录本地读取时刻并区分标注（「数据读取于 …」vs「服务端生成于 …」）。（前端 0.25d）

**迭代3 收口新暴露的残留（已实测，一并排进本轮）**：
- T4.5 项目级 overview 的两块面板不随 scope（**后端遗留 L8 的后果**）：`overview` 页的**让步账本**读 `s.dashboard.accepted`、**度量实验**读 `s.dashboard.metricTrend`，两者都是**顶层字段**，因此在项目 scope 下仍显示全局内容。实测：非法 scope（"未知项目"）页上照旧列出全局运行 #1298–#1317 与 `cmd/metricgate-mcp/main.go:35` 的让步 —— 与迭代 1 修的 scope 隔离是同一类问题，只是换了两块面板。根因：`ProjectSummary`（`internal/cockpit/dashboard.go:62-77`）不带 `accepted`/`metricTrend`/`summary` 三个字段，前端只能在顶层读（`app.js:1890`、`app.js:1921` 均有注释说明），`smoke.mjs:498-523` 有 L8 tripwire 盯着：**一旦后端补上字段，前端必须同步改成 scope 感知**。（后端 0.5d + 前端 0.5d）
- T4.6 空态与在飞态统一（本轮只覆盖了 3 处）：`loadPending` 已插进 projects / runs / issues 三处空态，但 `calls` / `activity` / `rules` / `gate` / `measures` 的空态仍只看列表是否为空、不看 `loading`。慢库上同样会短暂把"没读到"画成"没有"。（前端 0.5d）

## 五、给项目经理的一句话

骨架和工程质量是过关的（真实浏览器里首屏 7 个项目、路由/刷新/面包屑/键盘导航都正常）。验收时的**两条阻断级问题**（问题分诊接口 30s 超时整页空、进项目看到隔壁项目数据与策略）**已在迭代 1 修复并实测收口**（issues 37.03s→2.86s；policy 按 scope 返回 `root`；非法 scope 400）。**迭代 3「补引导」也已收口**：问题分诊默认收敛到「本项目 + 最新 1 次运行 + 未处理」（首屏 142 条而非 3.7 万条，一键放宽到 60 次运行得 858 条）、runs 页不再把未归属冒充全局、项目卡片区分有调用/仅运行/空、规则页从 138 个配置键变成 17 行真正的规则目录、错误态不再与「0 个问题」同屏、服务端错误正文可见。**下一步是迭代 2（门禁自相矛盾）与迭代 4（打磨 + T4.5 的项目级面板 scope 残留）**；排期总计约 **15–16 人日**，4 个迭代，前后端部分任务可并行。逐条验收证据：`docs/iterations/cockpit-ui/iter-05-p0-availability-and-scope.md` §8（迭代 1）、`docs/iterations/cockpit-ui/iter-06-p2-guidance-and-honest-empty-states.md` §9（迭代 3）。
